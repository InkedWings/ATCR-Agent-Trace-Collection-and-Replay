# cc=1/2/4 数据分析与单推理节点补跑建议

分析日期：2026-09-07。数据来自 `trace_framework/runs/scaling/single-backend-cc124-20260907-2`；大纲依据项目根目录 `sigconf.tex`。本次新增分析文件，不改动原始结果、实验配置或运行中的任务。

**结论：六个点的执行和计数有效，可以保留为探索性结果；目前尚不足以作为论文中的容量上限、稳定 p95 或严格的并发加速比。优先补齐任务覆盖和重复实验，再做缓存、部署配置及工具后端对照。**

## 数据范围与口径

- 单独一台推理节点 `x3005c0s1b1n0`，另外一台回放/工具节点 `x3005c0s1b0n0`。因此当前结果应称为“单推理节点、固定回放资源”，不能直接写成全部组件同机的单节点部署。
- Qwen3-32B BF16，vLLM 0.19.1，4 张 A100，TP=4、DP=1；上下文 32768；`max_num_seqs=32`、`max_num_batched_tokens=2048`、显存比例 0.90；prefix caching 开启。
- 每个点重启推理服务，预热 120 秒，测量 600 秒，停止新任务后等待已进入任务自然完成。每点只跑一次，任务池顺序使用 seed=42。
- cc 包括任务 setup、replay、cleanup。它不等同于正在执行的 LLM 请求数。
- 下表吞吐是窗口内完成任务数 / 600 秒；任务延迟属于窗口内启动的任务，包含窗口结束后的完整延迟。两个统计群体不同。
- `summary.csv` 原有的 backend active tokens/s 排除了后端没有活跃请求的时间。下面另列输出 token / 600 秒，用于解释整个部署的利用情况。

## 有哪些问题

### 1. 执行和计数没有发现损坏，但 valid 的含义有限

本次逐任务检查 89 个生命周期的报告、节点完成记录、源 trace 节点与输出 token 目标；核对窗口任务数、后端 token 事件及结束请求计数。六个点全部完成、未截断，客户端输出 token、后端输出 token 与 vLLM 全程 generation counter 一致。窗口 token 按事件时间重算。

`valid=true` 只说明这套性能测量校验通过，不代表题目答对、工具全部成功，或实验已经具有统计代表性。原始失败尝试和 smoke 结果不混入本报告。

采样为近似一秒一次，600 秒通常得到 598–599 条，最大间隔 1.46 秒，未见明显长时间缺口。各点采样间隔和窗口边界空隙保存在 `checks.json`；不能仅以样本数不等于 600 判为丢数。

### 2. 任务覆盖不足，是当前最影响并发曲线的问题

| 工作负载 | 可用池 | cc=1 窗口启动的不同 trace | cc=2 | cc=4 |
|---|---:|---:|---:|---:|
| OpenClaw | 11 | 8 | 8 | 11 |
| mini-SWE | 10 | 2 | 5 | 8 |

同一个 seed 保证相同的入场序列，但低并发在固定时间里只走过序列前半段，高并发已经开始循环。预热又把不同任务移出延迟统计。因此各点并不是同样的任务组合。

mini-SWE 的任务吞吐从 cc=1 到 cc=4 表面上增长 4.5 倍，不能据此声称超线性扩展。cc=2 的 p95 从 336 秒降到 258 秒，也不能解释成系统延迟改善。

作为辅助诊断，比较三种 cc 都执行过的相同 trace 的首次生命周期，包含预热和 drain，不作为主窗口指标：

| 对齐的首次 trace | cc=1 平均，s | cc=2 平均，s | cc=4 平均，s |
|---|---:|---:|---:|
| OpenClaw，11 条 | 80.34 | 80.42 | 86.30 |
| mini-SWE，3 条 | 267.29 | 275.71 | 290.98 |

对齐之后 mini-SWE 的三个任务都随并发增加而变慢，与总体 p95 的表面改善不同。这说明任务组合的影响不可忽略。首次出现的位置、缓存状态仍有差异，所以此表只作诊断。

### 3. 缓存热度与并发混在一起

| 工作负载 | cc=1 prefix hit | cc=2 | cc=4 |
|---|---:|---:|---:|
| OpenClaw | 83.67% | 90.98% | 98.33% |
| mini-SWE | 97.07% | 96.46% | 96.92% |

OpenClaw 的 TTFT p95 从 0.803 / 0.815 秒下降到 0.280 秒，同时 hit ratio 明显上升。更高并发更早重复任务池，可能获得额外的跨任务重复前缀收益；同一任务中的上下文增长也带来正常的前缀复用。目前数据不能区分这两部分贡献。

服务每点初始空缓存，并不意味着 120 秒以后各点处于相同缓存状态。mini-SWE cc=1 尚未重放完首个任务，说明其高命中率也不能全部归因于跨轮重复。

需要 APC on/off 对照，并明确 on 条件允许哪些前缀共享。只有明确报告“有限任务池循环回放”的缓存条件，现有数值才有准确的解释。

### 4. 工具报错主要继承原 trace，另有两处回放差异

| 工作负载 | cc | 窗口工具调用 | 原生报错 | 报错率 | 原成功→回放失败 |
|---|---:|---:|---:|---:|---:|
| OpenClaw | 1 | 51 | 6 | 11.76% | 0 |
| OpenClaw | 2 | 81 | 8 | 9.88% | 0 |
| OpenClaw | 4 | 173 | 17 | 9.83% | 0 |
| mini-SWE | 1 | 114 | 19 | 16.67% | 0 |
| mini-SWE | 2 | 250 | 29 | 11.60% | 0 |
| mini-SWE | 4 | 434 | 48 | 11.06% | 0 |

全程而非只在窗口内检查，也没有“原成功→回放失败”的节点。OpenClaw 的原生错误均发生在原本标记为错误的 `web_fetch` 节点，日志可见 403、fetch failed、提取失败；mini-SWE 也均落在原本报错的 bash 节点。这些数量随任务数增长，不能直接解释为并发导致故障率上升。

mini-SWE 的 `pydicom__pydicom-1694` 中 `tool-046`、`tool-048` 在三个 cc 下均从原失败变为成功。命令为 `echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT && cat /tmp/patch.txt`；原记录是文件不存在，回放前序命令成功生成文件，而且回放执行器显式绑定任务级 `/tmp`。这与临时文件持久化差异相符，但当前报告只保存错误布尔值，未保留这些调用的实际返回内容，不能确定所有返回语义完全一致。

固定路径回放会继续执行后续记录，LLM 输入也不变，因此该差异没有导致分支变化；论文的回放保真验证仍须披露并检查它。适合补存返回码和简短错误类型，避免仅凭 `native_error` 判断工具执行一致性。

### 5. 当前池偏向短上下文，也没有 DAG 宽度变化

32768 上下文限制仅保留 GAIA 24 条中的 11 条、mini-SWE 22 条中的 10 条，分别排除了 54.2% 和 54.5%。mini-SWE 保留的 10 条仅包含候选池约 25.3% 的 LLM 调用和 22.9% 的输出 token，短轨迹偏差比按 trace 数看更明显。

依据已存 preflight token 数，若只放宽长度上限到 65536，长度上可容纳的候选数预计为 GAIA 21/24、mini-SWE 17/22。**这只是 token 长度筛选结果，不是显存或可运行性验证**；需要新配置的单请求 KV 显存检查。

现有 21 条可用 trace 都是线性链，OpenClaw 每条 5–23 个节点，mini-SWE 每条 60–160 个节点。现有结果能体现不同链长，不能支持大纲中 DAG 宽度、fork/join 和依赖结构的结论。

### 6. 与论文测量目标还存在缺口

- 当前是固定路径回放，不能直接当成实时生成决策的完整 agent 成功率/性能；大纲中“directly execute complete agentic workflows”需要真实 agent 对照，或改清楚研究边界。
- OpenClaw 窗口任务平均 setup 为 14.30 / 10.75 / 10.86 秒；mini-SWE 为 35.20 / 25.86 / 26.81 秒。现在每任务新建 runtime，和大纲中 persistent assistant 的部署条件不同，需要评估 runtime 复用的影响。
- 现有磁盘计数是节点块设备计数，不能用来填论文的 Lustre 文件系统 I/O 压力图。应添加目标路径对应的 Lustre 客户端计数或合适的进程 I/O profiling。
- 两种负载 cc=1 的 GPU 利用率都约 69%，工具调用平均延迟约 0.5–1.1 秒；这些结果尚不能替代 ChemGraph 的计算密集工具后端基线。
- `admission_wait_seconds` 当前代码计算的是任务启动时距实验起点的累计时间，并非外部请求从到达到获得槽位的排队等待。不能将它当成 frontend queue latency。

## cc=8/16/32 之外，优先跑什么

以下为建议矩阵，未提交新作业。`C*` 表示根据当前 cc=8/16/32 结果选出的吞吐转折区或满足预先定义延迟目标的代表并发；在看到结果之前不指定其值。

| 优先级 | 实验 | 最小建议配置 | 对应大纲及解决的问题 |
|---|---|---|---|
| P0 | 完整池覆盖与独立重复 | 两种负载先选 cc=1、C*、32；每点至少 3 次独立运行，采用配对的多个 seed，随机化点顺序；延长窗口到每次覆盖完整池并观察多个周期 | 单节点并发曲线、稳定性、可解释的 latency/throughput；现有六点保留为 pilot |
| P0 | 回放保真对照 | 两种负载 cc=1 各取短/长/报错 trace；同模型真实 agent 与 replay 对照；在 C* 做小规模复核 | 支撑 trajectory capture / controlled replay；检查调用数、token、工具结果状态和耗时构成。真实路径变化与执行开销需分开解释 |
| P0 | ChemGraph 基线 | 若保留三类负载叙事，先完成捕获与回放验证，再跑 cc=1/2/4；后续扩展范围按工具资源需求决定 | 科学 agent 与 tool-heavy 结论；记录 LLM、CPU/GPU 工具资源分配 |
| P1 | Prefix caching 消融 | 两种负载 cc=1、C*，APC on/off；on 复用正式基线，新增 off；代表点重复 | 区分缓存收益与并发收益；记录 hit/query、prefill、TTFT、KV |
| P1 | 生命周期与工具耗时消融 | 两种负载 cc=1、C*；每任务新 runtime vs 可安全重置的 runtime 池；另选 recorded-delay tools 对照真实 tools | 分解 setup、工具间歇、推理和编排开销；runtime 复用须保持任务状态隔离 |
| P1 | 单推理节点的 TP/DP 对照 | 在四卡总预算相同前提下，TP4×DP1 vs TP2×DP2；先显存预检，再选 C*、32 | 大纲的 inference deployment；TP2 两副本的 KV 余量可能受限，不能默认 32K+相同并发一定可运行 |
| P1/P2 | 长上下文敏感性 | 32K vs 64K，先 cc=1，再 C*；共同可运行子集用于配置因果比较，新增长 trace 另报覆盖与性能 | 降低短上下文过滤偏差；不能换池后直接把吞吐差都算作上下文设置影响 |
| P2 | 服务调度预算 | 先看 cc=32 的等待/KV/preemption；有瓶颈再测 `max_num_seqs=32/64`、batched tokens 2048/4096/8192，每次只改一个控制量 | 分清 task concurrency、服务端序列上限和 prefill 预算的影响 |
| P2 | DAG 结构微基准 | 线性链 vs fork/join；宽度 1/2/4，深度浅/深，控制总 LLM token 和工具工作量；选低并发与 C* | 补齐现有全线性轨迹无法回答的 DAG 问题 |
| P2 | 工具执行架构 | 先在 ChemGraph 的代表工具上比较 local、shared MCP、per-tool MCP、Parsl worker 配置；固定工具总资源 | 大纲的 tool-heavy microbenchmark；优先避免对短 bash 工具做庞大全组合 |

**最先安排的顺序：**等当前 cc=8/16/32 找到转折区 → 延长并重复 cc=1/代表并发/32 → prefix cache on/off → TP/DP 和 runtime/tool 对照。ChemGraph 捕获与基线是补齐论文工作负载范围的独立必做项。

完整池覆盖的时长要按慢负载预算：mini-SWE cc=1 的已有任务约 3.5–5.7 分钟一个，10 分钟窗口明显不足。可先按 30–60 分钟做预算估计，但最终以任务覆盖与多个周期是否稳定为准。多周期运行可能需要将两种负载拆到不同作业；当前每作业两小时、依次执行两种负载的布局未必容纳较长窗口和 drain。尾延迟要积累更多任务样本，三次重复本身不保证 p95 已可靠。

**cc=64 不宜抢先加：**只有 cc=32 后仍未出现吞吐转折，或者需要观察过载区时再扩展。`max_num_seqs=32` 不禁止 task cc=64；工具和 setup 会占据任务槽，但若同时 ready 的 LLM 请求超过 32，服务端预算会成为显式约束，应保留并解释。

**可留到多后端阶段：**跨节点 weak scaling、prefill/decode 分离、多后端路由。单副本时 round-robin 与 KV-aware routing 没有可选目标；若先部署 TP2×DP2，则可在同一推理节点做双副本路由小对照。Frontier 属于大纲的跨平台覆盖，宜复跑关键基线和转折点，无需先复制全部单机矩阵。
