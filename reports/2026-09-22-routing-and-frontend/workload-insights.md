# 从 agent 工作负载特性解释系统行为

2026-09-22。本文把 [跨实验组结论](insights.md) 进一步组织为工作负载机制：**多轮依赖使请求的计算成本和到达节奏都受到系统运行状态影响。固定 trace 控制了执行路径，却没有消除这种反馈。** P2 继续排除。

本文新增的统计只读取已有 trace CSV、实验汇总与逐后端统计，没有重跑实验。数值及口径见 [workload_features.json](workload_features.json)，复现脚本为 [workload_features.py](workload_features.py)。

1. **多轮上下文累积，使缓存能否持续复用成为轨迹实际计算成本的一部分。**

   同一条 trace 的动作与提交输入都可以固定，但其未缓存输入处理量仍为 `Σ(prompt_i − cached_i)`，取决于此前运行形成的缓存状态。新增统计中，逐 trace 的“累计提交输入 / 该 trace 最大单次输入”中位数为 OpenClaw **5.42**、mini-SWE **41.22**。该比值只描述多轮输入体量，不是实际重复 token 比例或可实现的缓存收益；但它说明仅看最大 context 无法表示整条轨迹的输入负载。

   简化解释：若一条 m 轮轨迹每轮稳定追加 Δ tokens，且历史不截断，则各轮 prompt 为 `H₀, H₀+Δ, …, H₀+(m−1)Δ`。完全不复用时，提交历史的输入处理量为 `mH₀ + Δm(m−1)/2`；理想保留公共前缀时，新增输入处理量可接近 `H₀+(m−1)Δ`。这说明轮数增加会扩大历史反复处理的潜在代价。**这是条件化的 token 记账模型，不是从当前 trace 拟合出的平方增长律，也不表示 attention FLOPs 或时间变成线性。**

   我们的系统证据是 OpenClaw 8192 的 cc16→64，每输出 token 对应未复用输入从 **10.32 增至 132.48**，输出吞吐同时下降约 61%。因此缓存状态可以改变同一种 agent 负载的实际计算需求；它不只是影响单次调用延迟的一个附加指标。

   设计含义：benchmark 应保留跨轮前缀与缓存历史，并报告实际未复用输入；不能将固定 trace 路径等同于固定的后端计算工作量。路由策略也会通过改变前缀复用来改变实际工作量，策略间不只是将一份固定成本的工作重新分配。

   证据：[Trace 画像](../2026-09-08-expanded-trace-analysis/README.md)、[请求级缓存诊断](../2026-09-16-kv-cache-cause/README.md)。

2. **LLM→工具→LLM 的交替，使计算活跃时间与历史状态的复用时间跨越不同边界。**

   一个 task 正在执行工具时，可能没有 LLM 请求在 GPU 上运行，但下一轮依然会引用此前历史。单次 LLM 调用结束与整条 agent 轨迹结束是不同事件；希望避免下一轮重算，就需要考虑历史状态跨调用的可用性。因此，“当前 running 少”不能推出“继续执行这些任务不需要历史状态”。

   请求级核对观察到，在同一后端上，相邻请求仍有 **147,623-token 公共前缀**，cached tokens 却从 **136,224 降至 5,280**。另一例有 31,635-token 公共前缀，cached tokens 从 29,040 降至 0。这直接说明相同前缀、相同目的后端还不足以保证有效复用；单节点逐 cache group 诊断进一步确认了 state group 截短最终复用的情况。

   这支持把“任务在生命周期内会再次使用什么状态”作为解释维度，而不仅看当下活跃请求占了多少 KV。它也解释了为什么 prefix affinity 与实际状态保留需要一起考虑。

   **边界：**尚未证明工具执行间隔就是本次状态丢失的触发因素。上述两对请求从前一次完成到下一次入队仅 0.77/0.95 s，但距前一次 cache lookup 已有约 72.7/47.8 s；状态可能在此前 decode 等阶段已变为不可用。因此未来可考察状态距上次命中、创建及下次使用的间隔，不能只把“工具耗时长”当作归因。

   证据：[同后端公共前缀核对](../2026-09-21-rr-hotspot-cause/README.md)。

3. **输入侧长尾可以被任务数量与输出侧统计掩盖；两类 agent 的压力结构也不同。**

   对每条原始 trace 只统计一次，按累计提交 Qwen 输入排序：OpenClaw 输入最多的 **11/110 条（10%）**贡献 **66.24% 的提交输入、39.18% 的 LLM calls，但仅 27.22% 的录制输出**。mini-SWE 前 **7/61 条（11.48%）**贡献 **38.67% 的输入、25.86% 的输出**。

   结合 OpenClaw 8 轮、mini-SWE 77 轮的中位数，以及累计输入/最大输入 5.42 vs 41.22 的差别，可以更具体地刻画这两个池：OpenClaw 的输入负载高度集中在少数轨迹；mini-SWE 更明显地体现长交互链反复携带历史。不能只用“一个更轻、一个更重”或平均输出长度概括两者。

   对系统的潜在影响是，少量高输入轨迹在复用失效时可能带来很大的额外 prefill 工作；但这是待验证的压力传播解释。**当前没有完成逐 trace 的退化贡献归因，不能断言正是这 11 条导致 CC 拐点。** 上述比例是提交输入体量，不是未命中输入、GPU 时间或正式测量窗口的实际访问权重；固定窗口的闭环回放也不保证各 trace 出现次数相同。

   设计含义：同时展示按 trace、调用和 token 加权的分布；做规模对比时保留长尾轨迹的覆盖情况。用一个“平均任务”替代原池会丢失这部分结构。

4. **串行依赖会把局部慢后端转化为其他后端的请求供给不足。**

   OpenClaw 1+8 RR 的热点 r07 接收 **12.5% 的窗口到达请求**，却占各后端平均 `running+waiting` 总和的约 **85.1%**。每个后端到达数都是 2006，但 r07 请求滞留均值 188 s，其余约 4.5–5.2 s。

   在固定活跃 task 数的回放中，task 的下一轮请求依赖当前轮完成。当很多 task 停在热点时，它们同时失去了继续给其他副本产生后续请求的能力。这意味着一个后端的服务退化，能够通过 agent 的依赖链影响其他后端的供给；局部高排队与其余后端低并发可以同时出现。

   一个简化解释是：给定访问份额下，较长的请求滞留会占用更多活跃 task；task 被占住后，整个闭环的请求产生速度又会下降。本轮窗口非稳态，不把任何稳态排队公式作为精确拟合。请求均分、滞留悬殊和队列集中是观测；这个反馈过程是与时间线相符的机制解释。

   这让 routing 的目标更具体：除了避免某个后端积压，还要保持足够多的 agent 能继续推进并产生后续工作。CA 的低排队、高复用与 2.63×/3.11× 窗口吞吐增益与此一致；现有实验尚不能分离负载反馈和亲和的各自贡献，也未定位最初形成热点的唯一扰动。

   证据：[到达和滞留](routing_arrivals.json)、[逐后端负载](replica_diagnostics.json)、[形成时间线](../2026-09-21-rr-hotspot-cause/README.md)。85.1% 是后端 gauge 均值的比例，不是精确的 task 占比。

5. **Task CC 是各执行阶段共同占用的名额，优化工具/环境会改变同一 CC 下的推理压力。**

   mini-SWE 总 CC 始终为 256、8 个 backend。若 task 群体接近满载、工作混合稳定且各调用基本串行，可以用 `LLM 阶段平均在途数 ≈ task CC × LLM 时间 / task 生命周期` 解释阶段占用；再除以后端数得到每后端估计。

   | 配置 | LLM 占任务生命周期 | 估计每后端 LLM 在途 | 实测每后端 running | 实测 waiting |
   |---|---:|---:|---:|---:|
   | 1+8，build4 | 60.76% | 19.44 | 18.89 | 0.05 |
   | 1+8，build8 | 62.10% | 19.87 | 19.17 | 0.07 |
   | 2+8，总 build4 | 84.72% | 27.11 | 26.45 | 0.10 |

   估计与实测的变化方向、数量级都一致：增加第二个前端后，原来耗在 setup/tools 的 task 名额更快进入 LLM 阶段，后端实际 running 提高约 40%，总 CC 并没有改变。这比单纯说“CPU 更快”更具体地解释了瓶颈之间如何联系。

   这也解释了 LLM 阶段均值 **485→624 s**、整体任务却 **799→737 s**、输出吞吐提高 **8.2%** 可以同时发生。下游阶段需要处理更多同时在途的请求，其墙钟耗时增长不等于 kernel 效率下降。另一方面，build4→8 没有增加物理资源，只把更多工作推入已饱和的前端，阶段占用和总吞吐都没有明显改善。

   **边界：**这是阶段占用关系的近似核对，不是精确恒等式。客户端阶段包含服务外的等待，任务 cohort 与后端固定窗口也不同；不能用约 0.5–0.7 个请求的估计差异推导具体开销。2+8 只证明更多后端工作伴随更好的整体表现，没有证明继续加速前端一定继续获益。

   设计含义：同一 task CC 在不同工具实现、前端配比甚至不同 cache 状态下，代表的推理压力都可能不同。单节点获得的 CC 运行区间需要连同工具/环境执行条件一起描述。

6. **可扩展的部署需要同时保留轨迹局部性和请求供给能力。**

   单节点增加 CC 会让更多活跃轨迹竞争同一后端的缓存与计算；当前 balanced weak scaling 则在每副本 CC 不变时复制本地缓存和前端供给，在 16 个推理副本上保持约 99%–101% 的 token 扩展效率。它说明维护每副本的工作条件是一条已验证的扩展方式。

   前端对照又表明这个条件不要求固定一前端配一后端：mini-SWE 2+8 可接近历史 8+8 吞吐，OpenClaw 1+8 仍有较多 CPU 余量。需要保持的是足够的供给能力，而非某个固定节点配比；历史 policy 差异使这些跨部署比值只能作为参考。

   Routing 决策同时影响未来可复用状态和当前负载。因而一个值得检验的设计方向是，在任务连续性和后端压力之间做选择，而不只均分单次调用。但目前还不能宣称某一种严格 task-sticky、状态保留策略或动态迁移阈值最优；CA 本身也同时包含亲和与负载反馈。

   证据：[Weak scaling](../2026-09-15-weak-scaling/README.md)、[前端与 routing 合并分析](README.md)。

**适用于当前证据的文章论点**

> 多轮 agent 执行同时具有跨调用的状态复用和下一步依赖。前者使每次请求的实际计算需求依赖缓存历史，后者使后续到达依赖前面调用与工具的完成速度。我们的结果显示，这两种依赖能够把缓存退化放大成全局供给不足，并使前端优化改变相同任务并发下的推理压力。因此，评估 agentic workload 需要联合保留状态复用、阶段时序和闭环推进，而仅匹配请求长度或总并发不足以保留其系统行为。

这些机制也可能出现在其他有状态闭环系统中，不宣称为 agent 独有。本文的证据范围仍是两个固定池、当前模型/引擎和单次运行；没有控制缓存驻留时间或专门干预少数长尾 trace，不能将相关推断写成已经完成的因果消融。Replay 固定 recorded 输入和后续路径，新输出不改变轨迹；对真实在线 agent 的行为变化不作结论。
