# Agentic benchmark：跨实验组的 insights 与归因

2026-09-22。综合 trace analysis、单推理节点 CC sweep、balanced weak scaling、前后端配比与 RR/cache-aware 对比。P2 暂不纳入。这里只使用实测值，区分直接观测、机制解释和未验证的推广。

进一步结合多轮上下文、工具间隔、输入长尾与闭环依赖的解释，见 [从 agent 特性出发的机制分析](workload-insights.md)；包含新补算的输入集中度、阶段占用与热点在途比例。

**文章主线：agentic workload 的性能由交互历史、前端请求供给和后端缓存/排队状态共同决定。工作负载与部署改变的不只是请求数量，还会改变每个请求实际需要做多少计算，以及下一轮请求何时产生。因此，增加任务并发、复制推理副本、增加环境创建名额和改变路由，可能产生完全不同的性能结果。**

以下 F+B 表示 frontend 节点数 + 推理 backend 节点数，每个 backend 使用 TP4。当前结论适用于所测 Qwen3.6-35B-A3B / vLLM 0.19.1 和两类固定 trace 池；不解释为所有模型、agent 或引擎版本的普遍定律。

1. **Agent 的跨轮历史复用需要完整的模型状态：即使 attention KV 仍在，GDN 状态缺失也会增加重复 prefill，并可能使高并发吞吐退化。**

   **核心结论：**在当前 Qwen3.6-35B-A3B / vLLM 0.19.1 配置中，agent 下一轮能否从历史前缀继续计算，同时取决于 attention KV 和对应边界的 GDN 状态是否可用。提高任务 CC 会增加缓存竞争的风险；若 GDN 历史状态在下一轮复用前变得不可用，即使 attention KV 仍能命中很长的前缀，整个模型也必须退到更早的共同可用边界，重新处理后续历史输入。因此，固定 trace 的实际计算需求会随缓存状态变化，增加 CC 可能带来额外 prefill，而非只增加可批处理的请求数量。

   **两类缓存的区别：**GDN 全称为 Gated DeltaNet（门控 Delta 网络）。所测模型包含 30 层 GDN 和 10 层 full attention；attention KV 保存历史 tokens 的 K、V，GDN state cache 保存处理到特定位置时的递归状态快照。两者都由当前 vLLM 的公共 block pool 管理，但不是同一种状态。实际布局为 1 个 attention cache group 和 3 个 GDN state groups；最终复用需要各组在兼容边界上都满足条件。这里的“状态丢失”指计算快照不可复用，完整的历史输入仍随下一次请求发送，也不表示 GDN 的门控运算本身发生异常。[模型官方说明](https://huggingface.co/Qwen/Qwen3.6-35B-A3B)、[GDN 原始论文](https://arxiv.org/abs/2412.06464)

   **直接证据：attention KV 尚存，但状态组限制了复用。** 在同一个 OpenClaw cc32、budget8192 的 30 分钟诊断运行中，同一 trace 的同一 LLM 步骤较早和较晚两次执行如下；它们不是 cc16 与 cc64 的受控对照。

   | 指标 | 较早一次 | 较晚一次 |
   |---|---:|---:|
   | Prompt tokens | 168,814 | 168,814 |
   | Attention 可命中 tokens | 167,904 | 167,904 |
   | GDN state 限制后的最终复用 tokens | 167,904 | 4,752 |
   | 未复用、需要处理的输入 tokens | 910 | 164,062 |
   | 输出 tokens | 71 | 71 |
   | 后端 scheduled → first token | 0.426 s | 9.275 s |

   两次后端初始排队都约 3 微秒。较晚一次的前序调用约 30 秒前还成功命中过 143,088-token 的完整状态；相邻输入共有 168,330 tokens 的相同前缀，覆盖该边界，下一次却无法再命中该状态。这直接支持历史状态可用性损失，而不是输入历史被修改。按实际 admission 统计，该 8192 短窗口中，state 组相对 attention 可命中长度截掉的 tokens 占全部未复用输入的 57.43%；这是 token 工作量比例，不是 GPU 时间占比或可恢复吞吐预测。

   **与 CC 的关系：有证据支持的机制链。**

   `任务 CC 增加 → 活跃缓存占用及分配竞争可能上升 → 旧 GDN 状态更难保留到下一轮 → 完整可复用前缀缩短 → 额外 prefill 增加 → 输出吞吐可能下降。`

   当前 `align` 路径不会在每个 attention block 边界保留一份独立的 GDN 状态。GDN 向前计算主要需要最新状态，旧快照可能在当前调用仍执行时就失去引用、进入可回收队列；后续分配再移除其旧缓存映射。因此“agent 任务尚未结束”不保证旧快照仍受保护。`kv_cache_usage` 统计活跃、不可回收块的比例，free 队列中也可能保留历史缓存；不到 100% 仍可能发生历史状态淘汰，也不要求发生 OOM 或请求抢占。这里的重计算是未命中前缀后的额外 prefill，不能仅用抢占后的 recompute 计数衡量。[状态管理代码](https://github.com/vllm-project/vllm/blob/v0.19.1/vllm/v1/core/single_type_kv_cache_manager.py)、[公共缓存池代码](https://github.com/vllm-project/vllm/blob/v0.19.1/vllm/v1/core/block_pool.py)

   OpenClaw 8192 长窗口的趋势与这一机制相符：

   | Task CC | 输出 tokens/s | 实际 prompt 复用 | 未复用输入 / 输出 token |
   |---|---:|---:|---:|
   | 16 | 433.58 | 93.95% | 10.32 |
   | 32 | 282.41 | 68.87% | 50.76 |
   | 64 | 167.29 | 9.24% | 132.48 |

   cc64 每单位输出对应的未复用输入约为 cc16 的 12.8 倍，说明增加并发伴随更大的输入处理负担；这不是 FLOPs 或 GPU 时间比例，也不能将长窗口全部损失都归为 GDN。长窗口缺少同样的逐组 lookup 日志，可能同时包含 attention KV 淘汰等影响。

   **与 agentic workload 的关系：计算可以暂时停止，历史复用需求仍然存在。** 多轮 `LLM → tools → LLM` 使历史状态需要跨调用保留，上下文增长又可能提高丢失后的重算代价。在其他请求负载相近时，工具等待越长，旧状态暴露于缓存替换的时间越长；但固定 task CC 下，所有任务工具变慢也可能减少实际 LLM 并发、缓解竞争，因此不能断言工具越慢命中率必然越低。真正相关的是从状态不再受保护到再次使用之间的分配竞争，而不只是工具耗时。

   工具等待的独立作用尚未量化。已有 RR 请求对从前一次完成到下一次入队仅 0.77/0.95 s，仍出现同后端、相同公共前缀的复用损失；前一次 lookup 距下一次请求却已有约 72.7/47.8 s，旧状态可能在此前 decode 阶段就变得不可用。长工具等待不是这些复用损失的必要条件，也不能把具体淘汰时刻直接定位到工具阶段。

   **区别于另一项调度问题：**旧 2048 sweep 中，两类任务继续提高 CC 也曾发生吞吐下降；匹配的 cc32 短窗口 A/B 表明，2048→8192 使 waiting 请求因 block 对齐而得到零 token 配额的事件比例从 34.95% 降至 3.00%，吞吐提高 46.9%，同时缓存块数量略有下降。这是入场调度限制，与本条的状态复用损失应分别归因；增大预算缓解前者，但没有消除后者。

   **证据边界与 benchmark 含义：**已确认 attention 命中很长而 GDN 状态匹配缩短、实际未复用输入增加。旧状态被回收后覆盖是源码与观测共同支持的解释，但没有逐块创建、释放和覆盖日志，尚不能定位哪个请求覆盖了哪个块，也不能把全部 CC 退化归为唯一 bug。缓存替换是通用机制；attention KV 尚在却受递归状态约束，是混合架构额外的复用条件，不能直接推广到所有模型。Task CC 不等于实际 LLM running，拐点还取决于上下文、阶段耗时、容量与保留策略。当前 OpenClaw cc16、mini-SWE cc32 是已验证的 8192 稳定运行点，不是全局最优；mini-SWE 8192/cc64 在环境创建阶段失败，没有性能结论。

   Benchmark 应同时报告各 cache group 的命中边界、最终实际复用、未复用输入、阶段间隔及实际 running/waiting；仅凭 KV usage 或 attention 命中率不足以判断有效历史复用。请求处理变慢又可能加重后续竞争，是与观测相符的放大过程，尚未由受控干预量化。

   **论文表述：**在所测混合架构后端中，agent 的跨轮历史复用依赖 attention KV 与递归状态的共同可用性。高并发下，即使 attention KV 仍可命中，GDN 状态的可用性损失也会缩短有效前缀并增加重复 prefill。因此，任务并发会通过缓存状态改变实际输入计算量；评估 agent 吞吐需要同时考察跨调用状态保留，而不能只依据活跃 KV 占用或单次请求规模。

   证据：[逐组缓存诊断及请求记录](../2026-09-16-kv-cache-cause/README.md)、[8192 长窗口](../2026-09-16-single-backend-8192-check/README.md)、[预算 A/B](../2026-09-14-token-budget-comparison/README.md)、[相邻调用时间线](../2026-09-21-rr-hotspot-cause/README.md)。

2. **Trace 的交互链长度和跨轮历史复用，是区分 agent 工作负载的重要维度。**

   当前池为 OpenClaw 110 条、mini-SWE 61 条。每条 trace 的 LLM calls 中位数分别为 8 与 77，累计 Qwen 输入分别约 0.155M 与 1.486M tokens，均相差约 9.6 倍；每任务最大 prompt 的中位数却仅为 30,333 与 40,995，约 1.35 倍。mini-SWE 的累计请求负载更高，与更多轮交互反复携带历史上下文一致，不能只用“单次 prompt 更长”解释。

   两个池的尾部也不同：OpenClaw 每任务最大 prompt 的 p95 约 107.6k，mini-SWE 约 79.5k；较短的交互链不保证更小的单次长上下文压力。这是样本结构差异，还不能单独据此解释两者不同的 CC 拐点。

   工具 API 同样不足以表示系统成本：OpenClaw 的 web_search/web_fetch/exec 约占 48.2%/31.4%/19.2%；mini-SWE 全部标为 bash，却覆盖代码阅读、修改、测试等不同操作。其环境创建成本也不在单纯 tool-call 数量中。本次 replay 的 web_search 为 recorded delay，本地 bash 则实际执行，CPU 供给需求自然不同。

   对 benchmark 的含义：保留 LLM/tool 的依赖顺序、prompt 增长、跨轮公共前缀、输出长度以及环境/工具执行语义；仅匹配总 token 数或 API 调用数，不能声称已经匹配 agent 负载。累计输入包含反复传入的历史，不能视为唯一信息量或实际未命中的 prefill 量。采集侧 reasoning 占原始输出约 60.1%/31.3%，也说明最终可见答案长度不足以代表生成负载；该比例来自 Nemotron 采集，不能直接当作 Qwen 自主推理的组成。

   证据：[Trace 分析](../2026-09-08-expanded-trace-analysis/README.md)、[逐指标分布](../2026-09-08-expanded-trace-analysis/summary.csv)。

3. **保持每副本的稳定运行条件后，横向复制可以近线性扩展；这与单节点增加 CC 后退化并不矛盾。**

   Balanced weak scaling 同时增加 frontend 与推理副本，固定 OpenClaw cc16、mini-SWE cc32。扩到 **16 个推理副本 + 16 个 frontend，共 32 个物理节点**时，输出为 **7027.79 / 11446.85 tokens/s**，相对各自 1+1 基线的 token 扩展效率为 **101.30% / 99.07%**。缓存复用基本保持约 94% / 95.6%，副本间吞吐 CV 分别不超过约 0.91% / 1.56%（该版报告已测规模）。

   解释是扩展时同时复制了请求供给资源与本地缓存，且每副本的 task CC 和 sticky 映射保持不变；无需将更多活跃任务挤入同一个后端。单节点 CC sweep 增加的是同一组有限资源承受的并发，而 weak scaling 增加了资源。因此两组结果共同支持“先确定稳定工作区间，再复制这个部署单元”的扩展方式。

   这只说明在当前独立副本、固定池、循环回放和所测规模内，没有观察到显著的全局扩展开销；不是单请求跨节点加速，也没有验证全局共享 KV、不同 TP/DP 布局或不断到达新任务时的效率。101.30% 是单次运行的轻微差异，不能据此宣称超线性加速。旧 weak-scaling 报告中的理论占位不进入结论；OpenClaw 4 推理副本的新实测已在合并报告中使用。

   证据：[Weak scaling](../2026-09-15-weak-scaling/README.md)、[合并实测索引](sources.json)。

4. **前端与推理资源需要按 workload 配比；balanced 布局的线性扩展不意味着必须一前端配一后端。**

   固定 8 个推理节点时，OpenClaw 1+8 的 CPU 均值约 **35.43%**，输出 3453.22 tokens/s，保留历史 8+8 吞吐的约 **98.36%**。mini-SWE 1+8 的 CPU 已到 **95.79%**，输出 5259.45 tokens/s，仅约历史 8+8 的 **92.27%**。

   新增 mini-SWE 2+8、每前端 2 个 build 名额、合计名额仍为 4，得到 **5690.48 tokens/s**，比 1+8/build4 提高 **8.20%**，两个前端 CPU 均约 45%；这接近历史 8+8 的 5699.78 tokens/s。与当前 1+8 相比，它直接支持增加前端资源能改善 mini-SWE 供给；与历史 8+8 相比，它提供了用更少前端获得相近吞吐的部署证据。

   归因依据是两类任务的环境和工具执行方式不同，并与本次 CPU、创建等待、工具耗时变化相符。采集 trace 中 LLM 阶段占时较高，也不能保证规模扩大后永远由推理端限制：当大量工具与环境工作集中到一个前端时，共享资源竞争会改变阶段耗时。

   历史 balanced 使用不同 HTTP/build policy，98.36%、92.27% 和 99.84% 是部署参考，不能全部视为严格仅改变前端数量的 A/B。新增前端也同时增加内存带宽与本地 I/O，不能将收益百分之百归给 CPU。2+8 是已测有效配置，尚不足以宣称成本最优比例；Polaris 前端也是 GPU 节点，资源节省需按实际使用/申请节点解释，不等于云上 CPU-only frontend 的价格结论。

   证据：[合并分析第 2、4 部分](README.md)、[前端对照图](figures/01_frontend_controls.png)。

5. **提高软件并行上限不能替代资源扩容；瓶颈缓解后，下游 LLM 阶段甚至可能更长。**

   mini-SWE 两个控制实验将这个机制分得更清楚：

   | 配置 | 输出 tokens/s | CPU / 前端 | build 名额等待均值 | 实际 build 均值 | 每任务 tools 阶段均值 |
   |---|---:|---:|---:|---:|---:|
   | 1+8，4 个名额 | 5259.45 | 95.79% | 97.29 s | 12.72 s | 194.72 s |
   | 1+8，8 个名额 | 5204.49 | 98.09% | 11.09 s | 21.04 s | 257.44 s |
   | 2+8，总计 4 个名额 | 5690.48 | 44.98% | 0.94 s | 5.32 s | 102.62 s |

   **直接观测：**放宽 build 名额显著减少了显式等待，却没有吞吐改善；创建和工具工作本身更慢，CPU 更满。增加前端资源则同时降低等待、创建和工具阶段时间。

   **机制解释：**名额等待只是前端供给链的一部分。放宽名额把更多工作移入已经饱和的前端，增加环境构建与工具执行之间的资源竞争，不能凭等待队列缩短就判定服务能力提高。低于 0.12% 的 iowait 和超过 442 GiB 的最低可用内存也不支持将本次问题解释为存储容量或内存耗尽。

   另一个非直观结果是，2+8 的 LLM 阶段均值从 **485.18 s 增至 624.42 s**，同时整体任务生命周期从 **798.55 s 降至 737.05 s**，吞吐提高。逐后端平均 running 从 **18.89 增至 26.45**：前端更快释放了原先停留在 setup/tools 的任务，使更多任务进入推理阶段。这支持并发在阶段间重新分布的解释；不是 LLM kernel 变慢的直接证据。不同运行的任务组成和缓存历史仍有差异，不能精确量化所有阶段变化的因果贡献。

   对 benchmark 的含义：task CC 包含 setup、LLM、tools、cleanup，不等于 GPU 上同时运行的请求数；每阶段的等待与服务时间、实际 running/waiting 都要一起测。

   证据：[耗时分解与箱线图](figures/02_frontend_time_breakdown.png)、[前端时间序列](figures/03_frontend_timeseries.png)、[配置和资源明细](analysis.json)。

6. **RR 均分请求数，仍可能在闭环 agent workload 中维持单后端热点。**

   新 OpenClaw 1+8 RR 中，每个后端在窗口内都收到 **2006 个请求**；r07 的 running/waiting 均值却为 **39.82 / 61.85**，其它副本 running 约 2.3–2.8、waiting 小于 0.1。r07 请求滞留均值为 **188.26 s**，其它副本约 **4.46–5.18 s**；实际复用分别为 **13.90%** 与约 **67%–69%**。到达数量均分没有使请求滞留均衡。

   已有 1+4 请求级核对还排除了一个过于简单的解释：在热点转折附近，两次相邻调用到达同一后端、真实公共前缀仍覆盖先前命中部分，cached tokens 仍可由 OpenClaw 的 136,224 降至 5,280，或 mini-SWE 的 29,040 降至 0。因此本地缓存可用性本身也会下降，不能把全部损失解释为“换后端造成 cache miss”。

   与观测相符的反馈链是：

   `局部复用下降 → 更多输入需要 prefill → 请求推进变慢 → RR 继续送入相同份额 → 在途积压 → 缓存/调度压力加重。`

   agent 的下一步依赖当前 LLM 调用完成；固定数量的活跃任务逐渐停在慢后端，后续总请求产生变慢，其他后端便会排空。这解释为什么最终可以出现“一处高排队、其它处低并发”。单节点 CC sweep 已说明服务能力随缓存与负载变化，因此不能用“同型号 GPU，所以各副本服务速度始终相同”来否定这个现象。worker 的 task CC 也不限制 router 目的后端的在途请求数。

   **证据边界：**请求均分、同后端公共前缀复用损失、在途热点和时间演变均已观测；反馈链是支持度较高的机制解释。热点最初为何落在某一个副本、哪个 cache group/块何时失效，以及节点运行时差异的贡献，尚未完全识别。不能宣称 RR 必然产生一个热点、某编号必然异常或已经定位唯一 bug。

   证据：[N8 逐后端统计](replica_diagnostics.csv)、[N8 到达与滞留](routing_arrivals.json)、[N4 前缀及起因核对](../2026-09-21-rr-hotspot-cause/README.md)。

7. **Cache-aware 的价值在于同时改善复用和负载状态；当前收益不能全部归为前缀亲和。**

   相同 1+4 配置与官方 router 路径下，RR→cache-aware：

   | 指标 | OpenClaw | mini-SWE |
   |---|---:|---:|
   | 输出 tokens/s | 614.59 → 1618.49（2.63×） | 775.60 → 2412.67（3.11×） |
   | 实际前缀复用 | 63.48% → 90.58% | 59.49% → 88.58% |
   | 相邻调用切换后端 | 73.91% → 17.18% | 74.64% → 16.11% |
   | CA 各后端 waiting 均值 | 0.09–0.19 | 0.33–0.60 |

   同一任务更少迁移，与提高历史复用、降低未复用输入工作量相符。同时官方 cache-aware 会在负载不均时选择低负载副本；记录中显式不均衡分支占其决策约 **13.19% / 11.19%**。低前缀匹配时也可能走低负载选择，因此这两个比例不是所有负载反馈决策的总占比。[对应版本策略源码](https://github.com/vllm-project/router/blob/v0.1.15/src/policies/cache_aware.rs)

   因而这是“亲和 + 负载反馈”的整体策略收益，不能分配成缓存机制独占的贡献；它使用近似前缀历史，也不等于掌握精确的 GPU resident KV。更好的平衡体现在没有持续的单后端积压、总吞吐更高，不要求所有副本输出完全相等。例如 OpenClaw 的逐后端输出 CV 在 CA 下为 11.49%，高于 RR 的 5.75%，但排队反而均衡得多。

   OpenClaw RR 点非稳态；mini-SWE RR 只使用完整恢复窗口，不使用被 drain 截断的任务尾延迟。2.63×/3.11× 是当前固定窗口的实测比值，不是跨运行显著性或长期稳定容量倍数。N8 CA 尚缺有效数据，暂不能外推策略收益随节点数如何变化。

   证据：[匹配配置、吞吐与局部性](../2026-09-21-routing-and-fixed-frontend/README.md)、[负载反馈计数](../2026-09-21-routing-and-fixed-frontend/router_feedback.json)、[更新对比图](figures/04_routing_comparison.png)。

8. **扩展比例、资源忙碌程度和平均吞吐，需要与有效工作及时间稳定性分别评估。**

   OpenClaw RR 4→8 的窗口输出增长 **2.03×**，但 1+8 RR 仅达到同规模 sticky 部署输出的 **36.11%**，甚至低于 1+4 cache-aware。它说明一种效率较低的运行状态也可以随资源增加而近线性扩大。Sticky 直连与 router 的协议路径不同，36.11% 只作部署对比；严格策略对照仍使用 RR/CA 相同 router 路径。

   N8 RR 前/后半窗口输出从 **1327.79 降至 1166.27 tokens/s**，waiting 从平均每后端 **7.16 增至 8.42**。一分钟或整窗均值无法替代稳态证据。mini-SWE build8 虽通过原 steady 阈值，创建名额等待仍从前半窗口 2.73 s 增至后半窗口 19.56 s；吞吐阈值通过也不等于所有队列稳定。

   资源指标亦有类似限制：旧 mini-SWE cc32→64 的 GPU busy 约 96.0%→96.6%，但输出吞吐下降超过一半、本地 prefill token/s 接近四倍。GPU 在忙，不代表它在高效产生输出。KV usage 统计活跃、不可回收块；free 队列中也可以保有历史前缀，后续分配会覆盖它们，因此低 KV gauge 不能证明缓存没有淘汰，高 KV gauge 也不保证实际复用率高。[对应版本 block pool](https://github.com/vllm-project/vllm/blob/v0.19.1/vllm/v1/core/block_pool.py)

   对 benchmark 的含义：将窗口 token/task 吞吐、完整任务延迟、实际 token 复用、未复用输入负担、逐后端在途/排队、前端阶段耗时与 CPU 一起报告。保留时间序列和完整 admission cohort；不要仅用全局平均、GPU busy 或 KV 曲线判断容量。数据完整性与稳态分开，任务回放完成与工具执行结果一致性也分开。

   证据：[RR 时间趋势](figures/06_openclaw_rr_scaling.png)、[旧 mini-SWE CC 分解](../2026-09-13-minisweagent-qwen36-scale/README.md)、[缓存指标机制](../2026-09-16-kv-cache-cause/README.md)。

**论文可直接使用的综合表述**

> 在所测 agent trace replay 中，多轮交互同时产生可复用的历史上下文和串行的请求依赖。系统吞吐取决于前端能否持续供给请求，以及后端能否在并发下保留可用的历史状态。单副本增加任务并发可能因复用下降而增加输入计算，造成输出吞吐退化；保持已验证的每副本运行条件并增加独立副本，则在所测规模内接近线性扩展。前端控制实验表明，资源扩容和放宽软件并行上限具有不同效果；路由实验表明，均分请求数量不能保证均衡服务压力。由此，agentic benchmark 应在完整工作流中联合评价吞吐、延迟、请求局部性及跨阶段资源供给，而不能只依据孤立的推理吞吐或扩展比率。

**统一适用范围**

- 这些是两类 workload、当前模型/引擎/硬件下的实测与解释；没有覆盖模型/引擎版本的充分交叉对照，不能判定机制只属于某一个模型或版本。
- 每点一次运行。时间分箱、不同请求或副本不作为独立实验重复，不报告统计显著性或“已找到最优”。
- 轨迹原始采集用 Nemotron；Qwen replay 固定后续 recorded prompt、工具动作与目标输出长度，新生成内容不改变后续路径。它提高系统比较的可控性，同时不测在线 agent 的决策质量；对 state cache 的潜在影响尚未独立量化。
- 固定池循环与充分 warmup 有利于复用，不能将约 94%–96% 的复用直接推广到持续新任务或冷缓存。
- web_search 以录制 delay 重放，不能据此声称测得真实搜索服务容量。环境/原生工具成本与错误单独报告，trace replay 完成不等于解题成功。
- 前端节点数对历史 balanced 的比较有 HTTP/build policy 差异；P2、启动失败点及理论占位均不作为机制或性能结论的证据。
