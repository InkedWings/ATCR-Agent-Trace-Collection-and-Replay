# 单后端、扩展与路由：已有证据支持的归因

后续更新：本批运行现已结束，完整窗口结果、drain 超时处理与图表见 [2026-09-21 完整结果分析](../2026-09-21-routing-and-fixed-frontend/README.md)。本文件保留当时前 45 分钟的中途观察，最新定量结论请使用后续报告。

2026-09-21。主线：agent replay 的服务能力由实际前缀复用、未命中输入计算量和前端工具/环境供给共同决定；增加副本、提高每副本并发和改变路由可能走向不同的性能区域。

## 数据边界

- 单后端 8192、balanced weak scaling，以及 fixed-frontend OpenClaw 1+2/1+4、mini-SWE 1+2 使用已完成结果。
- 最新 6 个实验仍在运行。本报告固定取每个实验 **正式 measurement 开始后的前 2700 秒**，不包含 warmup，不把部分窗口标成正式完成结果。所有结论中的新倍率均是中途趋势，尚未做完整 drain、客户端/后端总计数和最终稳态验收。
- Token 计数来自 vLLM Prometheus 边界采样增量。每个边界取第一条不早于目标时刻的记录，最大偏移小于 1 秒；各副本吞吐按自身实际采样间隔计算后相加。复用率按 cached/prompt 总 token 加权；未复用输入取 `source=local_compute`。
- TTFT 是同一计数窗口的**后端均值**，不是客户端 p95 或按完整任务 cohort 统计的尾延迟。
- Frontend CPU 使用窗口内全部约 1 秒采样；后端 gauge 仅每 300 秒取一个样本，作为辅助诊断，不能当作完整采样的窗口均值。
- 路由 RR/cache-aware 已核对 serve、trace pool、profile、router 参数、HTTP 策略、cc、seed、warmup/measurement 和前缀复用设置一致。策略改变也会改变闭环负载的 trace 进度及组成；没有逐请求配对或跨 run 重复实验。
- 当前工作负载是固定 trace pool 循环回放、新生成内容不替换后续录制 prompt；不能直接外推到持续到达的新任务或真实生成反馈的 agent 运行。

原始引用、采样边界、每副本指标见 [partial_metrics.json](partial_metrics.json)，路由与环境等待见 [routing_and_setup.json](routing_and_setup.json)。读取程序 [analyze_partial.py](analyze_partial.py) 对后端大文件按时间定位，只读边界及稀疏采样；未启动任何新实验。

## 1. 路由改变了实际计算负担，均匀分请求并不足够

同样 1 个 frontend + 4 个 TP4 后端，前 45 分钟：

| Workload | 策略 | 输出 tokens/s | 实际 prompt 复用 | 未复用输入 / 输出 token | 后端平均 TTFT |
|---|---|---:|---:|---:|---:|
| OpenClaw | RR | 637.97 | 63.13% | 59.15 | 6.37 s |
| OpenClaw | cache-aware | 1619.31 | 90.63% | 15.81 | 0.64 s |
| mini-SWE | RR | 799.80 | 58.64% | 62.54 | 15.35 s |
| mini-SWE | cache-aware | 2382.05 | 88.50% | 17.98 | 0.64 s |

Cache-aware 的输出吞吐分别为 RR 的 **2.54× / 2.98×**。RR 每单位输出对应的未复用输入分别为 cache-aware 的 **3.74× / 3.48×**。窗口内平均 prompt 长度分别为 OpenClaw 45,747/48,231、mini-SWE 28,922/29,321 tokens，两策略输入长度均值相近，主要差异出现在实际复用和未复用计算。

实际 routing ledger 中，取窗口内至少观察到 8 次调用的 task，相邻调用换后端的比例为：

| Workload | RR | cache-aware |
|---|---:|---:|
| OpenClaw | 73.53% | 17.44% |
| mini-SWE | 75.12% | 16.11% |

这支持“路由频繁改变目的后端 → 局部前缀难以复用 → 更多 prefill 工作 → 首 token 更慢、吞吐降低”的机制链。这里直接测到了迁移、复用和计算量；缓存块如何被创建/覆盖仍未在本轮逐块记录。样本只包含截至读取时已写出的路由记录，且至少 8 次调用的筛选不代表全部任务。

RR 的副本输出吞吐反而更均匀：OpenClaw CV 6.83% vs 10.80%，mini-SWE 3.16% vs 5.47%。所以“各副本负载更平均”本身不能保证更高总吞吐。Cache-aware 可在存在一定副本差异时，靠更低的输入计算负担取得收益；当前不能把它解释为完全消除了负载不均衡。

## 2. mini-SWE 在 1+8 已进入前端与环境创建共同受限的区域

| 前 45 分钟 | OpenClaw 1+8 | mini-SWE 1+8 |
|---|---:|---:|
| 输出 tokens/s | 3444.41 | 5396.68 |
| Frontend CPU 均值 | 34.88% | 95.41% |
| Frontend CPU p95 | 49.89% | 99.53% |
| 一分钟 CPU 均值 ≥90% 的窗口 | 0/45 | 44/45 |
| 实际 prompt 复用 | 93.98% | 96.41% |
| Frontend iowait 均值 | 0.00037% | 0.136% |

mini-SWE 前端最少仍有约 458 GiB 可用内存、1972 GiB 本地 scratch 空间。该段 CPU 持续饱和，而前缀复用仍高，证据指向前端资源与准备流程；不支持把这段压力主要归为历史的后端 cache-hit 崩落或磁盘容量不足。

842 个在窗口内接纳的任务均已写出 sandbox setup 记录：

- 等待 4 个 sandbox 创建名额：均值 **65.61 s**，中位数 **34.06 s**，p95 **246.06 s**。
- 实际创建耗时：均值 **12.48 s**，中位数 **11.85 s**，p95 **18.38 s**。
- 相比之下，mini-SWE 1+4 cache-aware 的创建均值为 5.10 s，名额等待均值仅 0.0069 s。

以 4 个创建名额、12.48 s 平均创建时间粗算，创建能力约为 **19.2 tasks/min**；本段接纳 842/45≈18.7 tasks/min，与此接近。这是创建能力估计与接纳速率，**不是正式任务完成吞吐**，cohort 的部分创建时间也可能跨越窗口边界。

因此 CPU 饱和是直接观测事实，但吞吐受限究竟有多少来自整节点算力、有多少来自构建并发上限，目前不能分开。仅取消创建限流也可能加剧 CPU 竞争；不能直接宣称“加 frontend 一定恢复多少吞吐”。

## 3. 后端优化会把压力转移到前端

mini-SWE 从 RR 到 cache-aware：吞吐增加 2.98 倍，同时 frontend CPU 从 **12.41% 增至 36.31%**（2.93 倍）。OpenClaw 的相应倍率为吞吐 2.54、CPU 2.55。按输出吞吐归一化后，前端 CPU busy 时间非常接近。

这支持“后端加快后，闭环 replay 更频繁地触发工具与框架工作”的解释。CPU 利用率较低可能是上游进展慢的结果，不能单凭 RR 的低 CPU 宣称其前端更高效。归一化的 CPU 指标仍是整个节点的观测，不能精确拆为 router 与工具各自消耗。

## 4. 线性 weak scaling 与单副本高并发回落可以同时成立

已完成的 OpenClaw 单后端 8192：cc16→32→64，输出吞吐 **433.58→282.41→167.29 tokens/s**；实际复用 **93.95%→68.87%→9.24%**；每单位输出对应未复用输入 **10.32→50.76→132.48**。高并发的服务计算负担已经变化，不能把它当成固定服务时间下的普通排队平台。

Balanced 扩到 16 个后端时，OpenClaw/mini-SWE 的 token 扩展效率仍为 **101.3% / 99.1%**。其每副本 cc、完整 trace pool 和 task-sticky 路由保持不变，因此各后端维持了类似的并发与复用条件。这是复制已验证工作点的扩展结果，不证明单副本可以无限提高 cc，也不是跨节点 TP 加速。

更直接的机制证据来自旧诊断：相同 168,814-token 请求，两次 attention 都可命中 167,904 tokens，但 state 限制使其中一次最终只复用 4,752 tokens，后端 scheduled→first-token 从 0.426 s 增到 9.275 s。两个短窗口中，state 截短占全部未复用输入约 57%–62%。这已经超过“KV 图显示不对”的解释，但该比例不能外推到长窗口 cc64 或当前 routing。

另外，2048→8192 的匹配 A/B 将对齐后零 token allowance 事件/调度步比例从 34.95% 降到 3.00%，吞吐提高 46.9%。说明调度预算不足和 hybrid state 匹配损失是需要分别处理的两条机制。

详细来源：[单后端结果](../2026-09-16-single-backend-8192-check/README.md)、[KV 请求级证据](../2026-09-16-kv-cache-cause/README.md)、[budget 对照](../2026-09-14-token-budget-comparison/README.md)、[weak scaling](../2026-09-15-weak-scaling/README.md)。

## 5. Balanced 的前端配置并非成本最优

已完成的 OpenClaw 4 个后端实测：4 frontend + 4 backend 为 **1752.97 tokens/s**；1 frontend + 4 backend 为 **1747.21 tokens/s**，相差约 0.33%。实验实际使用节点由 8 降到 5，减少 37.5%，而固定前端 CPU 均值仅 14.72%。

这支持当前 OpenClaw 的前端可以合并部署。该比较存在旧/new HTTP 连接策略差异，是跨运行的部署趋势，不能当成严格只改变前端数的因果试验；小于 1% 的差别也不具统计显著性。mini-SWE 的前端成本更高，不能直接沿用 OpenClaw 的最佳配比。

## 最小后续归因验证（本报告没有提交）

1. 先等当前 6 个实验完成，复核完整窗口、自然 drain、失败任务与请求/token 对账，将这里的中途结果替换为正式值，并比较 trace 组成及时间稳定性。
2. 缓存归因：同一官方路由与协议下，加每 call 独立 cache salt 的对照；观察 RR/cache-aware 差距是否收缩，从而区分缓存收益与其余调度/均衡影响。
3. 前端归因：在 mini-SWE 8 后端、总 cc256 下，分别改变 frontend 数和 sandbox 创建上限。前端 1→2 的对照须维持总创建名额一致；构建上限 4→8 的对照须保持 frontend=1。记录等待、创建/工具耗时和后端供给，不能把两个变量同时改变后的增益全算给 CPU。
4. 对最终支撑论文主结论的路由和前端拐点做独立重复；本轮单次实验与窗口内波动不产生跨 run 置信区间。
